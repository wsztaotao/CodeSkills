# 闭环研发四阶段（更深，不更大）

目标：每个阶段可独立验收、可回滚；产出少而硬，拒绝扩范围。

## 硬门禁（未过门不得进入下一阶段）

1. **文档即真相**：每阶段只认带版本号的产物；口头约定必须回写文档。
2. **确认门**：`intent.md` 经需求方确认后才能 Design；`spec.md` 确认后才能写 `plan.md`；`plan.md` 确认后才能改代码；测试失败必须反馈需求方，不得 silently 改目标。
3. **禁止区 Hooks**：开工前写出不可碰清单（路径、配置、密钥、生产数据、外部账号、已冻结接口）；任何步骤触及禁止区必须停并询问。
4. **外部 Skill**：只引入 GitHub 上广泛验证、可复现的 Skill；先下载到项目目录并说明用途与质量收益，**征得同意后**才启用。
5. **更深优先**：改设计或改题时先加深约束与证明，不增加功能面。

## 阶段产物与版本

目录建议：`docs/loop/<phase>/vMAJOR.MINOR/`（或等价版本控制）。每版含：`STATUS`（draft|confirmed|superseded）、摘要、相对上一版 diff 要点、回滚说明。

| 阶段 | 产物 | 进入条件 | 退出条件 |
|------|------|----------|----------|
| Plan | `intent.md` | 接到需求 | 需求方确认意图与边界，无未决歧义 |
| Design | `spec.md` | intent 已确认 | 需求方确认施工图（接口、数据、失败路径、验收） |
| Build | `plan.md` → 代码 | spec 已确认且 plan 已确认 | 按 plan 完成；偏离必须改 plan 并再确认 |
| Test/Deploy | 测试报告 + 部署记录 | 有可测构建 | 独立验证通过或问题已回报需求方 |

回滚：检出上一 confirmed 版本文档，并按该版 `plan`/`spec` 恢复代码与配置；禁止只回代码不回文档。

## Plan：反问到无理解偏差

做：
- 列出目标、非目标、约束、成功标准、风险。
- 对含糊词（“更好”“尽快”“完整”）必须提问，不得猜测填充。
- 写清验收证据形态（日志、指标、用例、对照实验）。

产出 `intent.md` 最少章节：背景与目标；范围内/外；角色与权限；成功标准；开放问题（确认后应变空或已答）；禁止区初稿。

不做：未确认就写实现细节或扩需求。

## Design：代码施工图 `spec.md`

做：
- 模块边界、接口契约、数据形状、错误与重试、安全与密级、可观测性。
- 每个关键行为对应可测断言；标明当前周期内可交付的切片。
- 对照 `intent` 做追溯表：需求条目 → 设计段落 → 拟测点。

不做：把 `spec` 写成愿望清单；不写无法周期内验收的指标。

## Build：先 `plan.md` 后改码

`plan.md` 最少含：任务切片（可独立合并）、触及文件、风险与回滚、测试计划、禁止区复核。

规则：
- 需求方确认 plan 前 **零** 业务代码改动（只读探查除外）。
- 实现中发现设计缺口：停 → 升版 `spec`/`plan` → 再确认 → 再改。
- 提交信息引用文档版本号。

## Test/Deploy：独立验证

做：
- 另起独立测试代理或等价隔离会话，只拿 `spec`/`plan` 与构建产物，不共享实现聊天上下文。
- 失败分级：阻塞 / 可延期；阻塞项必须反馈需求方并附复现步骤。
- 部署记录含版本、配置哈希、回滚命令。

## 引入优质 Skill 的固定流程

1. 按任务检索 GitHub 上星多、近期维护、有人复现的 Skill/工作流。
2. 下载到项目 `skills/` 或约定目录，**不自动启用**。
3. 向需求方报告：名称、链接、用途、如何提升本项目质量、风险与替代。
4. 同意后再写入 Hooks/配置并在 `plan` 中引用。

## Hooks：禁止区清单模板

在 `hooks/do-not-touch.md`（或项目约定路径）维护：

- 不可改路径/文件
- 不可触达的环境与密钥
- 不可调用的生产接口
- 不可删除的数据
- 不可静默升级的依赖
- 必须人工确认的操作（发信、付费、对外发布）

每次阶段入口朗读并勾选；变更禁止区须升版并确认。

## 完成定义

- 四阶段均有 confirmed 版本文档；代码与文档版本可互指。
- 测试由独立路径执行，结果已回报。
- 禁止区未被突破；外部 Skill 均经同意。
